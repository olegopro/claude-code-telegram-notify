# Внутреннее устройство и грабли

Заметки для тех, кто правит код. Здесь только то, что не видно из самих скриптов: проверенное
поведение Claude Code и Telegram, замеры, ловушки и способы проверки.

> **Репозиторий публичный.** Сюда нельзя писать личное: токены и ключи, `chat_id`, `session_id`,
> почту, имена машин и папок, личные пути. Заметки об окружении (какая машина как достижима, какие
> опции где включены) держите вне репозитория — например, в `docs/*.local.md`: такие файлы
> игнорируются git (`.gitignore`).

## 1. Карта кода

| Файл | Что внутри |
|---|---|

| `hooks/tg-notify-lib.sh` | примитивы Bot API: `tg_send` (текст + необязательная клавиатура) `tg_edit` `tg_edit_kb` `tg_cb_answer` `tg_updates` `tg_delete` `tg_api`; `tg_bg` (вызов в фоне), `tg_where` (строки 📁/💻 шапки), `tg_host`, `tg_esc`, `tg_log` |
| `install.sh` / `uninstall.sh` | регистрация хуков в `settings.json` (идемпотентно, с бэкапом) |
| `tests/*.bats` | установщик и вопросы против mock Bot API |
| `tests/mock-telegram.py` | mock Bot API: честный длинный опрос, задержка сети, управление нажатиями |
| `tests/e2e/tui-question.py` | сквозная проверка на **живом** Claude Code (см. §6) |

Состояние в `/tmp` (на машину, не на репозиторий):

| Файл | Назначение |
|---|---|
| `claude_notif_<sid>` | время старта хода (для порога «Завершено») |
| `claude_notif_msg_<sid>` | `message_id` сообщений, которые снимет следующее действие в терминале |
| `claude_tg_q_<sid>` | ожидающий диалог: `pending <pid> <rid> <fp> [sub]` (`fp` — отпечаток запроса, `sub` — запрос фонового агента); пишет только ждущий хук |
| `claude_tg_q_<sid>.ans` | JSON ответов из терминала: пишет `answered`, читает и убирает ждущий хук |
| `claude_tg_q_<sid>.ev.<pid>`, `.resp.<pid>`, `.rc.<pid>` | пачка событий, ответ `getUpdates` и ссылка Remote Control текущего хука (убираются на выходе) |

Флаги и настройки: `~/.claude/telegram-notify.on` (общий выключатель), `telegram-question.on`
(вопросы кнопками), `telegram-permission.on` (разрешения кнопками, по умолчанию выключено), `telegram-notify.debug` (журнал в `/tmp/claude_notif_debug.log`),
`telegram-min-seconds`; переменные — в README, раздел «Настройка».

## 2. Вопросы `AskUserQuestion`: как это работает

Проверено на Claude Code **2.1.294** (в том числе при `permissions.defaultMode: bypassPermissions`).
Документация описывает только сам механизм (`updatedInput` с полем `answers`); поведение хука
относительно диалога в терминале в ней не описано — оно получено экспериментом (§6).

**Схема инструмента.** 1–4 вопроса; у каждого `question`, `header` (до 12 символов), 2–4 `options`
(`label`, `description`, необязательный `preview`) и `multiSelect`. «Other / Type something» и
«Chat about this» добавляет сам интерфейс — их нет в `options`.

**Формат ответа** (`updatedInput.answers`): ключ — текст вопроса; значение — метка варианта;
для чекбоксов — метки через `", "`; для своего текста — сам текст. `updatedInput` **заменяет ввод
целиком** — исходные `questions` нужно вернуть вместе с `answers`.

**Что делает хук `PermissionRequest` (matcher `AskUserQuestion`):**

| Ситуация | Что происходит |
|---|---|
| Диалог показан | хук стартует сразу и идёт **параллельно** диалогу; ответ хука закрывает диалог, ответ в диалоге — отдельно |
| Решение `allow` + `updatedInput` | диалог закрывается сам, модель получает ответы |
| Ответили в терминале (вариант или свой текст) | хук **не останавливается**; приходит `PostToolUse` с `tool_response.answers` |
| Esc в диалоге | хуку приходит SIGTERM, `PostToolUse` нет |
| «Chat about this» | хук жив, `PostToolUse` нет; позже приходит только `Stop` |
| Ответили через Remote Control | то же, что в терминале (`PostToolUse`) |
| `Notification` `permission_prompt` | приходит через ~6 с после показа диалога, текст «Claude needs your permission» без вопроса |

Отсюда конструкция: ждущий хук сам следит за файлами состояния (`claude_tg_q_<sid>` и `.ans`), а
`PostToolUse` (`answered`), `Stop`, `UserPromptSubmit`, `SessionEnd` только отмечают, что диалог
закрыт: `answered` кладёт ответы в `.ans`, остальные снимают `claude_tg_q_<sid>`. Два файла, а не
один, потому что «ответили» и «закрыли» приходят почти одновременно и не должны затирать друг друга.

**Обычные запросы разрешений (подкоманда `permission`).** Тот же `PermissionRequest`, без matcher:
вход — `tool_name` и `tool_input` (без `tool_use_id`), выход — `decision.behavior` `allow`/`deny`
(`deny` ещё и `message` — её читает модель). Что важно:

- **«Свой» запрос узнаётся по отпечатку** (`q_fingerprint`: имя инструмента + канонический `tool_input`,
  `jq -S`), потому что `PostToolUse` приходит без связи с запросом, а инструменты бывают параллельными.
  У `AskUserQuestion` в отпечаток входят только `questions`: `PostToolUse` приходит уже с `answers`.
- Для `PostToolUse` по любому инструменту хук `answered` — синхронный (порядок относительно `Stop`
  важен) и дешёвый: нет файла состояния — выход.
- **Запрос фонового агента.** Хук, сработавший внутри субагента, получает на вход `agent_id` (и
  `agent_type`). Такой диалог по-прежнему ждёт ответа в терминале, когда главный агент уже закончил
  ход или принял новый промпт, — поэтому `prompt` / `Stop` его не снимают, пока хук жив (`sub` в файле
  состояния). Диалог главного агента ход по-прежнему закрывает.
- **Решения по умолчанию нет**: сбой, таймаут, сигнал, недоступный Telegram — ни `allow`, ни `deny`.
- Ответ **обычным reply** на сообщение-запрос ничего не решает (только ответ на подсказку «причина»):
  «ок» нельзя трактовать ни как согласие, ни как отказ.
- Получив `deny`, Claude Code **может прибить хук сразу** — всё, что хук делает после вывода решения,
  может не успеть; поэтому файл решения (`TELEGRAM_DECISION_FILE`) пишется раньше stdout.
- **Команда хука не должна быть конвейером** (`… | tee`): `sh -c` умирает по SIGTERM раньше хука, и
  Claude Code добивает группу, не дав хуку прибрать сообщение (Esc → «зависшие» кнопки).

**Чего нет.** В `claude -p` инструмента `AskUserQuestion` модели не предлагается вообще (там и
вопросов нет). Официальные Channels (плагин Telegram, `--channels`) пересылают разрешения на
инструменты (Bash/Write/Edit); про `AskUserQuestion` в документации не сказано, нужны Bun и флаг
на каждый запуск — это отдельный путь, наш хук с ним не конфликтует, но бот должен быть другой.

## 3. Telegram Bot API: тонкости

- **`getUpdates` — один потребитель на бота.** `offset=N` подтверждает (удаляет) **все** обновления
  с меньшим id, в том числе чужие. Поэтому хук подтверждает только свои: `offset` не поднимается
  выше самого старого чужого живого обновления (`pin`). Так один бот живёт на несколько сессий и
  машин без блокировок.
- **Чужое «живое» и «мёртвое».** Нажатие кнопки с чужим `rid`: свежее сообщение (младше таймаута
  хука + 10 мин) — `pin`, не трогаем; старше — `stale`: отвечаем «вопрос закрыт» и снимаем
  клавиатуру. У `callback_query` нет собственной метки времени — берётся `message.date`.
- **409 Conflict.** Два одновременных long-poll на одном боте обрывают друг друга; вебхук делает
  `getUpdates` недоступным вовсе. Обновления не теряются (неподтверждённые остаются), хук просто
  повторяет опрос. Снять вебхук: `deleteWebhook`.
- **Длинный опрос и «мусор» в очереди.** Если в очереди есть неподтверждённые (чужие) обновления,
  `getUpdates` возвращается **сразу**, не ожидая `timeout`. Поэтому цикл не крутится вхолостую:
  если опрос вернулся быстрее секунды и ничего не принёс, хук спит `TELEGRAM_QUESTION_POLL`.
- **`callback_data` ≤ 64 байт.** Формат `q<rid>:<экран>:<действие>` (`o<N>` вариант, `t` свой текст,
  `d` готово, `p` назад, `x` вперёд, `s` отправить, `e<N>` к вопросу N с экрана проверки).
- **`answerCallbackQuery` обязателен** — иначе на кнопке крутятся «часики»; текст до 200 символов.
- **ForceReply** открывает поле ввода; ответ приходит как `message.reply_to_message`. Принимается
  ответ и на сам вопрос (без кнопки «Свой вариант»). Обычные сообщения без reply игнорируются.
- **Бот может удалять входящие** сообщения в личном чате — так убирается текст «своего варианта».
- **`editMessageText` без `reply_markup` снимает клавиатуру**; «message is not modified» — безвредная
  ошибка, молча игнорируется.
- **Лимит 4096 символов.** Вопрос, варианты и `preview` обрезаются в jq; всё экранируется под HTML.
- **Проверка отправителя.** Принимаются только обновления из чата `TELEGRAM_CHAT_ID`.
- **Идемпотентность.** Обработанные `update_id` хранятся в `seen`: обновление может прийти повторно,
  пока не подтверждён offset.

## 4. Скорость

Один вызов Bot API — это новое соединение: CONNECT через прокси + TLS 1.3 + запрос ≈ **3 RTT**.
Через VPN замерено ≈ **1,2 с на вызов**, напрямую ≈ 0,9 с; протокол уже оптимальный
(TLS 1.3, HTTP/2). Из `curl` без постоянного соединения быстрее не будет.

Что сделано, чтобы нажатие не копило вызовы:

| Приём | Эффект |
|---|---|
| Длинный опрос `getUpdates` (до 5 с, `TELEGRAM_QUESTION_LONGPOLL`) | ответ приходит в момент нажатия, без ожидания цикла |
| `answerCallbackQuery`, удаления служебных сообщений — в фоне | не стоят в очереди перед правкой |
| Снятие уведомлений (`drop_messages`) — параллельно и в фоне | синхронные хуки `UserPromptSubmit` / `PreToolUse` не ждут по ~1 с на каждое сообщение |
| Итог на выходе (правка, снятие подсказки, подтверждение offset) — тремя параллельными вызовами; ссылка Remote Control и название диалога читаются параллельно | один круг до Telegram вместо трёх; на старте — меньше работы до первого сообщения |
| Одна правка сообщения на пачку нажатий (`q_dirty`) | серия тапов по чекбоксам не даёт серию правок |
| Правка в фоне, следующий опрос идёт параллельно, правки — строго по очереди | быстрые подряд нажатия не ждут «прогрева» нового соединения |
| Опрос — фоновый `curl` + `wait` | SIGTERM (Esc) обрабатывается сразу, а не после ответа сервера |

Замеры на mock с имитацией 1,2 с на вызов (было → стало): нажатие → следующий экран 3,5–4,6 → 1,6 с;
«Отправить» → решение хука 3,4 → 0,3 с; три быстрых нажатия по чекбоксам 4,3 → 3,1 с.

Что остаётся и почему: ≈ 1,5 с на нажатие — это правка сообщения по свежему соединению.
Варианты дальше: `TELEGRAM_CURL_OPTS='--noproxy api.telegram.org'` (≈ −0,25…0,35 с, если Telegram доступен
без прокси из окружения) или другой выход VPN. **Проверять замером на каждой машине:**
на одной из машин владельца прямого маршрута до Telegram нет (`curl --noproxy` упирается в таймаут),
прокси там обязателен — опцию включать только там, где она проверена, в локальном env-файле; постоянное соединение потребовало бы вспомогательного
процесса (например, на python3) — осознанно не сделано, это лишняя зависимость и демон.

Разбор шапки: заголовок диалога и ссылка Remote Control берутся `grep`-ом по транскрипту — на файле
в десятки мегабайт это ≈ 0,3 с до первого сообщения; профита от оптимизации мало.

## 5. Грабли

- **Имена переменных в `sh` общие на весь скрипт.** Состояние вопросов называлось `q_st`, как
  переменная чтения файла-состояния — ответы «пропадали» без ошибок. Теперь `q_sts`; новые
  переменные движка начинаются с `q_`, а имена не должны пересекаться с `sid` `tp` `in` `cmd` `m`.
- **Установка поверх ручной.** Ручная регистрация по `settings.hooks.json` пишет `$HOME/...`,
  установщик — абсолютный путь; без нормализации хуки дублировались и всё приходило дважды
  (`install.sh` сравнивает команды после подстановки `$HOME`).
- **Stop приходит через секунды после PostToolUse**, а ждущий хук проверяет состояние раз в ~5 с:
  ответ из терминала лежит отдельным файлом `.ans`, которого `Stop`/`prompt` (`q_close`) не трогают,
  иначе сообщение получало бы «Вопрос закрыт» вместо ответа.
- **Ход главного агента не должен закрывать запросы субагентов.** Найдено вживую: фоновый агент просил
  разрешение, пользователь отправил промпт — `UserPromptSubmit` снял состояние, кнопки в Telegram
  погасли («выход: closed»), а диалог в терминале остался. Отличие — `agent_id` во входе хука.
- **Принимаемые ответы-reply вычисляются, а не хранятся.** Список сообщений, ответ на которые считается
  текстом, строится в каждом опросе из того, что реально существует (`q_ids`). Хранимый список
  рассинхронизировался: при неудачной отправке подсказки «причина» ответ на само сообщение-запрос
  принимался как причина отказа.
- **Один диалог на сессию.** Состояние (`claude_tg_q_<sid>`) одно на сессию: два одновременных запроса в
  одной сессии (параллельные инструменты) — кнопки получает первый, второй остаётся терминалу.
- **Двойной тап.** Кнопки привязаны к номеру экрана; запоздавший тап по устаревшему экрану
  отклоняется («Экран уже обновился»), иначе «Вперёд» дважды перепрыгивал бы вопрос.
- **Решение хука печатается в stdout** — единственная подкоманда с выводом. Итоговая правка
  сообщения уходит в фоне со своими дескрипторами: иначе фоновый процесс держал бы канал, и Claude
  Code ждал бы его завершения.
- **POSIX sh.** Без `local`, `[[ ]]`, массивов, `echo -e`; shellcheck в CI с `-s sh`. Тесты гоняйте
  и под `dash` (как на Linux), и под системным `sh` macOS.
- **`jq`.** Длинные программы проверять отдельным прогоном: ошибка скобок даёт пустой вывод, а не
  понятное сообщение; для `eval` использовать `@sh`.
- **`pkill -f` по шаблону `tg-notify.sh question` убьёт и рабочие хуки открытых сессий.** Для
  отладки убивать конкретный pid (`$!`), а mock — по `mock-telegram.py`.

Грабли тестов:

- В bats `! команда` **не роняет тест**; проверять через `[ ! -f … ]`.
- `wait_for test "$(…)" …` вычисляет подстановку один раз — нужен ленивый предикат (`state_is`).
- Фоновые процессы в bats держат дескриптор 3 — запускать с `3>&-`.
- Прокси в окружении разработчика ломает обращения к `127.0.0.1` — помощники теста идут с
  `--noproxy '*'`.
- Текст сообщений содержит HTML-теги: искать `📋 <b>Название</b>`, а не `📋 Название`.

## 6. Как проверять

```sh
bats tests/                                  # установщик + вопросы против mock (нужны bats, jq, python3)
PATH=/путь/к/шиму-sh-dash:$PATH bats tests/   # то же под dash
python3 tests/e2e/tui-question.py             # сквозной стенд на живом Claude Code (haiku, несколько запросов)
python3 tests/e2e/tui-question.py perm-allow perm-deny perm-terminal --claude ~/.local/bin/claude   # разрешения (режим default)
python3 tests/e2e/tui-question.py terminal esc --keep --claude ~/.local/bin/claude
```

**Сквозной стенд обязателен после обновления Claude Code**: unit-тесты не видят TUI, а вся
механика вопросов держится на недокументированном поведении (§2). Стенд поднимает mock Telegram,
ставит хуки настоящим `install.sh` в изолированный `CLAUDE_DIR` (так проверяются и регистрация,
и подстановка путей), запускает настоящий `claude` в pty с этими настройками (`--setting-sources
project --settings …`, пользовательские хуки не затрагиваются), нажимает кнопки через mock и сверяет:
ответы в решении хука (по файлу), итоговый текст сообщения, закрытие диалога.

Особенности автоматизации TUI:
- вывод TUI рисуется сдвигами курсора — в потоке нет пробелов, строки сравнивать без пробелов;
- в диалоге доверия к папке по умолчанию стоит «No, exit» — выбирать «Yes» стрелкой;
- `claude` в PATH может быть функцией оболочки — передавать `--claude <путь к бинарнику>`;
- через `--setting-sources project` не подхватывается блок `env` пользовательских настроек —
  прокси добавляется флагом `--proxy-from-settings`;
- команды хуков — **простые, без конвейера**, как в рабочей регистрации (её делает `install.sh`): через
  `| tee` сценарий `esc` ложно падал (см. §2); решение хук пишет в файл сам (`TELEGRAM_DECISION_FILE`),
  окружение хуков (mock, таймауты, `TELEGRAM_CURL_OPTS=--noproxy 127.0.0.1`) приходит из окружения
  `claude`, `HOME` не подменяется — нужна реальная авторизация;
- сценарии `perm-*` запускают Claude Code в режиме `default`, чтобы инструмент просил разрешение;
  команда с перенаправлением в файл — не «безопасная», её разрешение запрашивается всегда;
- bats-наборы нельзя гонять параллельно (dash и sh одновременно): тесты делят `/tmp/claude_*_t-*`;
- тест «выживает ли запрос субагента» делает длинный опрос коротким (`TELEGRAM_QUESTION_LONGPOLL=1`):
  при 5 с хук заметил бы снятие состояния слишком поздно, и тест прошёл бы и на сломанном коде.

Живая проверка на настоящем боте без Claude Code — команда из README, раздел «Проверка без Claude Code».

## 7. Выкладка на вторую машину (по ssh, без клона)

Хуки лежат копиями в `~/.claude/hooks/` на каждой машине, поэтому обновление нужно выкладывать
на обе. Проверенный порядок (доставка без клона на второй машине — через `git archive`):

1. Доставить закоммиченное: `git archive HEAD hooks install.sh | ssh <машина> 'mkdir -p /tmp/tg && tar -C /tmp/tg -xf -'`.
2. **Пробный прогон на копии настроек**: скопировать `settings.json` во временный HOME (пути
   домашней папки заменить на временную), запустить `HOME=… CLAUDE_DIR=… sh ./install.sh`,
   сравнить `jq -S .hooks` до и после — должно прибавиться ровно две записи, остальное
   идентично, по каждой подкоманде ровно одна запись.
3. Бэкапы: `settings.json`, прежний `settings.json.bak` (установщик его перезапишет) и оба скрипта.
4. Файлы хуков — **атомарной заменой** (`cp` во временный файл + `mv`): хуки открытых сессий
   исполняются прямо сейчас, и `cp` поверх выполняющегося `sh` может подсунуть им половину файла.
5. Запустить `install.sh`, проверить: валидность JSON, `sh -n`, совпадение md5 с репозиторием,
   флаги `telegram-notify.on` и `telegram-question.on`.
6. Не выставлять по умолчанию машинно-зависимое (`TELEGRAM_CURL_OPTS`, пороги): замерить на месте.
7. Показать формат вживую: отправить тестовое `ask` через `tg-notify.sh`, подождать, снять `permit`-ом.
